# OSTER CONFLICT — STADION OSTER ТЗ

Статус: `READY_FOR_IMPLEMENTATION`
Гілка: `stadion-oster`
Базова гілка: `r13-content-gameplay-pass`
Дата формування: 2026-08-20

## 1. Мета

Створити в Oster Conflict окрему локацію **«Стадіон Остер»** з жорсткою географічною прив’язкою до реальної місцевості, без змішування з музеєм, Сільпо, Будинком культури, автостанцією або іншими landmarks.

Локація повинна будуватись як окремий site block з власним placement owner. Жодна інша runtime-підсистема не має права пізніше переносити, замінювати або накладати на неї чужу геометрію.

## 2. Географічний anchor

### 2.1 Основний anchor стадіону

Верифікований публічний OSM/Mapcarta anchor центру стадіону:
- latitude: `50.94936`
- longitude: `30.88466`
- OSM way: `416516456`
- тип: `leisure=stadium`

Це **основна географічна точка**, від якої формується локальна UE-система координат для site block стадіону.

### 2.2 Контрольний anchor музею

Остерський краєзнавчий музей:
- latitude: `50.94831`
- longitude: `30.88400`
- OSM node: `8902097788`

За цими публічними anchors центр стадіону знаходиться приблизно за `126 м` від музею, напрямок від музею до центру стадіону приблизно `21.6°` від півночі, тобто NNE.

Локальне уточнення користувача також залишається обов’язковим: **якщо стояти обличчям до входу музею, стадіон сприймається зліва**. Це використовується як контроль орієнтації фасаду/підходу, а не як заміна GPS-anchor.

### 2.3 Контекстні anchors

Сільпо Остер:
- адреса: `вул. Богдана Хмельницького, 54`
- публічний map anchor приблизно `50.94907, 30.87621`

Автостанція Остер, контрольна точка з публічного map directory:
- приблизно `50.946396, 30.881088`

Остерський міський будинок культури:
- підтверджена адреса: `вул. Грановського, 3`
- цей landmark не належить до site block стадіону і не може використовувати його anchor.

## 3. Джерела референсів

Пріоритет:
1. фото, передані користувачем у робочому чаті;
2. дві карти користувача з підписаними реальними landmarks;
3. OSM/Mapcarta anchors;
4. офіційні дані Чернігівської ОДА про реконструкцію стадіону;
5. старі provisional координати в коді — лише як історичний матеріал, не як доказ.

## 4. Хронологія фото — не змішувати епохи

Набір користувача містить фото приблизно 2016, 2018, 2019, 2020, 2021 та 2025 років.

Правило:
- **поточний/модернізований стан** визначати за найновішими достовірними фото;
- старі фото використовувати для дерев, приватної забудови, контурів ділянки, стежок та історичних орієнтирів, якщо вони не суперечать новішим матеріалам;
- не змішувати старе ґрунтово-трав’яне основне поле з новим штучним покриттям так, ніби вони існують одночасно.

Офіційний опис реконструкції підтверджує для модернізованого комплексу:
- штучне газонне покриття футбольного поля;
- легкоатлетичні доріжки зі штучним покриттям;
- роздягальні;
- трибуни;
- санвузли;
- огорожу стадіону.

## 5. Просторова структура site block

### 5.1 Основне поле

Повинно мати реальний масштаб і орієнтацію за супутниковою картою та фото.

Обов’язково:
- футбольна геометрія;
- ворота відповідного типу;
- розмітка, якщо вона підтверджена фото поточного стану;
- покриття відповідно до актуального періоду;
- без гігантських професійних трибун, яких немає на референсах.

### 5.2 Старі/додаткові спортивні елементи

На фото зафіксовані:
- кілька футбольних воріт різного розміру;
- баскетбольні стійки/щити;
- вуличні тренажери;
- спортивні рами/перекладини;
- локальні витоптані/ґрунтові ділянки.

Їх розташування визначати по фотозв’язках, а не рівномірно розкидати по території.

### 5.3 Вхідна зона

За фото 2025 року присутня впізнавана синьо-жовта вхідна стела/вивіска `Стадіон Остер`.

Вона повинна бути окремою моделлю або окремим точним site prop.
Не замінювати generic табличкою.

### 5.4 Дерева та зелена межа

Стадіон сильно визначається деревами по периметру.

Потрібно відтворити:
- великі листяні дерева;
- окремі хвойні групи;
- щільну зелену межу з одного боку;
- нерівномірність насаджень;
- відкриті прогалини, які видно на фото.

Заборонено створювати рівномірну «паркову сітку» дерев.

### 5.5 Прилегла житлова забудова

Фото показують приватні одноповерхові/низькоповерхові будинки та паркани по краях стадіону.

Використовувати реальні наявні house/fence assets, якщо їх форма прийнятна.
Якщо потрібного фасаду немає — створювати окрему модель за фото, а не процедурний куб.

### 5.6 Стежки

Характерні вузькі ґрунтові пішохідні стежки є важливим орієнтиром.

Не робити їх асфальтованими дорогами.
Вони мають мати природну кривизну й ширину пішохідної стежки.

## 6. Жорстка прив’язка в UE

1. Додати canonical stadium geo anchor в спільну geo-reference систему.
2. Перетворення WGS84 → UE local coordinates має використовувати той самий origin/scale, що й інші підтверджені Oster anchors.
3. Не вводити окремий випадковий local origin тільки для стадіону.
4. Усі stadium components повинні бути дочірніми одного stadium site root.
5. Координати елементів усередині site block задаються як локальні offsets від stadium anchor.
6. Зміна global geo origin повинна зрушувати весь site block разом, без руйнування внутрішньої композиції.

## 7. Межі ownership

`stadion-oster` відповідає тільки за:
- стадіон;
- безпосередню прилеглу територію;
- видимі perimeter houses/fences/trees, потрібні для впізнаваності site;
- вхідну стелу;
- спортивне обладнання;
- локальні стежки;
- локальні service structures стадіону.

Не переносити сюди:
- музей;
- Сільпо;
- Будинок культури;
- автостанцію;
- центральний парк;
- коледж.

## 8. Asset policy

Перед створенням нової 3D-моделі:
1. перевірити `Content` на наявність схожого asset;
2. перевірити масштаб, pivot, collision, LOD і матеріали;
3. використати наявний asset, якщо він справді відповідає фото;
4. якщо не відповідає — створити окрему модель за фото;
5. не видавати blockout primitive за фінальну модель.

## 9. Photo reference policy

Для Oster Conflict діє постійне правило:
- якщо користувач прямо просить зберегти фото — зберігати;
- якщо користувач дає фото для створення 3D-моделі або локації — зберігати **обов’язково навіть без окремого прохання**;
- кожен photo pack повинен мати власну папку/документ-індекс і зв’язок з відповідним ТЗ;
- фото не видаляти після завершення моделі, бо вони є доказовою базою для майбутніх регресій.

Для цієї гілки canonical photo pack: `REFERENCE_PHOTOS/stadion_oster/`.

## 10. Acceptance criteria

Локація не може отримати `VERIFIED`, доки не виконано все:

### Географія
- stadium center сидить на canonical geo anchor;
- відносне положення до музею/міської сітки відповідає картам;
- site не накладається на музей, Сільпо чи інші landmarks.

### Візуал
- впізнається як реальний Стадіон Остер;
- правильна форма/масштаб поля;
- правильний характер зеленого периметра;
- присутні характерні ворота, спортивні елементи, стежки й прилегла забудова;
- вхідна стела відповідає фото;
- немає очевидних primitive placeholders у фінальному player-facing вигляді.

### Runtime
- немає flicker від пізнього replacement геометрії;
- немає дубльованих overlapping surfaces;
- collision поля, огорож, споруд і terrain коректна;
- FPS не деградує через зайві individual actors, використовувати ISM/HISM там, де це не шкодить точності;
- multiplayer/dedicated server behavior не ламається.

### Перевірка
- UE 5.8 build `Succeeded`;
- локальний gameplay test пройдено;
- користувач підтвердив географічне і візуальне розташування.

10. build;
11. playtest;
12. оновити `OSTER_CONFLICT_WORK_LEDGER.md` з commit SHA і результатом.

## 12. Заборонені скорочення

- Не ставити стадіон «приблизно біля музею» без geo transform.
- Не використовувати старий provisional anchor як final.
- Не будувати один великий cube як «стадіон».
- Не змішувати старі й нові фото без урахування року.
- Не називати `CODED_UNTESTED` результатом `VERIFIED`.
