# OSTER CONFLICT — MASTER ТЗ

> Постійне технічне завдання проекту. Це не разовий документ. Його потрібно оновлювати при кожній новій вимозі, зміні пріоритету або підтвердженому результаті playtest.

## 1. Призначення документа

Цей файл є єдиним реєстром того, **що Oster Conflict має робити і як виглядати**. Він не замінює код, Git history або короткі work reports, але визначає критерії приймання.

Перед будь-якою зміною в проекті потрібно прочитати:
1. `AGENTS.md`
2. `OSTER_CONFLICT_MASTER_TZ.md`
3. `OSTER_CONFLICT_WORK_LEDGER.md`
4. `OsterConflict/Docs/PROJECT_CONTEXT.md`

## 2. Статуси

- `TODO` — ще не почато.
- `IN_PROGRESS` — робота виконується.
- `CODED_UNTESTED` — код/asset підключений, але локальний UE playtest ще не підтвердив результат.
- `VERIFIED` — збірка пройшла і користувацький playtest підтвердив результат.
- `BLOCKED` — є конкретний blocker.
- `DEFERRED` — свідомо відкладено.

**Правило:** `CODED_UNTESTED` не можна називати «готово».

## 3. Definition of Done

Пункт вважається `VERIFIED` тільки якщо:
1. зміна існує в Git;
2. UE 5.8 build проходить;
3. runtime не падає;
4. користувацький playtest підтверджує саме потрібний результат;
5. `OSTER_CONFLICT_WORK_LEDGER.md` оновлений commit SHA та результатом тесту.

Якщо користувач повторює ту саму вимогу до `VERIFIED`, лічильник повторів у ledger збільшується. Повторне формулювання не створює нову задачу.

## 4. Джерела правди для географії та зовнішності

Пріоритет доказів:
1. пряме уточнення користувача після фактичного огляду/знання місцевості;
2. фото користувача;
3. верифіковані публічні фото/карти/панорами з інтернету;
4. підтверджені координати;
5. існуючий код/старі provisional anchors.

Старий код **не є доказом правильної географії**.

Заборонено позначати координату/розміщення як `verified`, якщо вона лише приблизна. Для приблизних точок використовувати `provisional`.

## 5. Архітектура локацій

Кожен великий landmark повинен мати власного власника placement/art logic. Одна підсистема не повинна пізніше перебудовувати або підміняти інший landmark після того, як гравець уже бачить сцену.

Обов'язково розділяти:
- Музей Остра;
- стадіон біля музею;
- схил/нижню житлову зону за музеєм;
- Сільпо;
- водонапірну вежу біля Сільпо;
- Будинок культури;
- коледж/технікум;
- парк;
- автостанцію;
- інші landmarks.

### 5.1 Музей — acceptance

- Будівля повинна впізнаватись як музей за референсами, а не як Будинок культури або Сільпо.
- Якщо стояти обличчям до входу музею, стадіон знаходиться ліворуч.
- За музеєм є перепад рельєфу і спуск вниз.
- Нижче спуску знаходиться приватна житлова забудова/хати.
- За музеєм не повинні випадково з'являтися парк, коледж або інші чужі landmarks.
- Не допускається змішування геометрії музею, Сільпо і Будинку культури в одному site block.
- Фото з інтернету використовуються для фасаду, пропорцій, даху, вікон, входу, двору та сусідніх орієнтирів.

### 5.2 Стадіон біля музею — acceptance

- Сторона відносно фасаду музею: **ліворуч**.
- Точна дистанція/центр залишаються provisional, доки не підтверджені джерелом або playtest.
- Стадіон не повинен перекривати музейну ділянку або нижній схил.

### 5.3 Схил і нижня житлова зона — acceptance

- Це реальний collision terrain, а не декоративна похила пластина поверх плоскої колізії.
- Перехід: музейна верхня ділянка → спуск → нижня тераса → житлова забудова.
- Хати, паркани, дерева та інші об'єкти повинні стояти по реальній висоті terrain, не зависати.
- При невдалому створенні нового terrain старий Ground не вимикається: fail-safe обов'язковий.

### 5.4 Сільпо — acceptance

- Окремий location block, не музейний site.
- Будівля, фасад, парковка, під'їзд і оточення звіряються з фото з інтернету.
- Неправильні legacy logo/text layers не повинні мерехтіти або накладатися один на один.
- Сільпо не може стояти на MuseumAnchor.
- Поруч у своєму правильному секторі має бути водонапірна вежа як окремий landmark.

### 5.5 Водонапірна вежа біля Сільпо — acceptance

- Окремий landmark/asset owner.
- Позиція визначається з фото/карти, а не з декоративної композиції.
- Масштаб, силует, матеріал і відстань до Сільпо звіряються з доступними референсами.

### 5.6 Будинок культури — acceptance

- Окрема будівля та окрема ділянка.
- Не спавниться в музейному site.
- Фасад, кількість/ритм колон, вхід, дах, прилегла територія і орієнтація звіряються з фото.
- Якщо точна географічна прив'язка не підтверджена, landmark не ставиться в завідомо неправильну точку лише для заповнення сцени.

### 5.7 Коледж/технікум і парк

- Неправильні старі runtime decorative layers залишаються вимкненими до правильної прив'язки.
- Не вигадувати точні координати без доказів.
- Після верифікації повернути як окремі site blocks.

## 6. Assets та візуальна якість

Пріоритет: **готовий реальний asset у `Content` → адаптація існуючого asset → процедурний blockout тільки як тимчасова заглушка**.

Не залишати видимі primitive cubes/spheres як фінальну геометрію, якщо в репозиторії вже є відповідна модель.

Наявні ресурси, які треба використовувати де доречно:
- `AdvancedVillagePack` houses, fences, trees, well, street lights;
- `VehicleVarietyPack`;
- imported R13 weapon assets;
- інші вже імпортовані Fab/Content assets після перевірки ліцензії та реального asset path.

Довгі паркани не розтягувати одним mesh до абсурдного scale. Реальні секції тайлити вздовж збереженої collision-лінії.

## 7. Runtime та стабільність

- Ніяких rebuild-pass, які видимо змінюють сцену через декілька секунд після появи гравця.
- Важкі procedural/site passes мають завершуватися під loading overlay або бути перенесені в стабільніший authoring pipeline.
- `PostLoadMap` сам по собі не означає, що player-facing scene готова.
- Не створювати UObject різних класів з однаковим ім'ям у тому самому Outer.
- Усі replacement-підсистеми повинні бути idempotent або мати чіткий guard/tag.
- Не лікувати геометричне мерехтіння VSync-ом, якщо причина — overlapping geometry або late runtime replacement.

## 8. Main menu / deployment UI

- Основний approved напрямок: `OSTER` тонким, `CONFLICT` великим жирним, `ОСТЕР • ГОЛОВНЕ МЕНЮ`.
- Фон меню не повинен на мить змінюватися на сірий/порожній shell.
- Наведення миші не повинно викликати layout jumping.
- ESC не повинен ламати WASD або Mouse X/Y після повернення в гру.
- Loading overlay повинен закривати незавершений runtime setup.

## 9. Gameplay test rack

Біля **фактичного spawn pawn**, а не біля умовної team-base точки, повинні з'являтися всі реалізовані test pickups.

Поточний набір: 11 класів, включно з anti-armor launcher.

Acceptance:
- усі pickup-и видно;
- вони не перекриваються;
- не провалюються в terrain;
- їх можна підбирати;
- imported weapon art застосовується;
- first-person debug arms/spheres/blocks не видно.

## 10. Git workflow

- Активна гілка R13: `r13-content-gameplay-pass`.
- Не робити force rewrite історії.
- Не комітити `Binaries`, `Intermediate`, `Saved`, `DerivedDataCache`.
- Коміти дрібні та тематичні.
- `main` отримує перевірені зміни через контрольований merge/forward-port; не робити сліпий merge великої конфліктної гілки.
- Якщо зміна ще не пройшла build/playtest, у ledger вона `CODED_UNTESTED`.

## 11. Обов'язковий цикл роботи

1. Прочитати MASTER ТЗ і WORK LEDGER.
2. Взяти найстаріший/найкритичніший незакритий пункт, особливо з повторними зауваженнями.
3. Перевірити існуючий код та assets перед додаванням нового.
4. Внести мінімальний тематичний commit.
5. Записати commit і фактичний стан у ledger.
6. Після локального build/playtest оновити статус.
7. Якщо користувач повторює вимогу — збільшити repeat count і не оголошувати її виконаною без `VERIFIED`.

## 12. Поточний пріоритет

1. Рознести та правильно прив'язати Музей / Сільпо / Будинок культури / водонапірну вежу.
2. Модернізувати ці локації за фото з інтернету та користувацькими фото.
3. Завершити музейний topology pass: стадіон зліва, схил позаду, нижні хати.
4. Прибрати late runtime rebuild та мерехтіння.
5. Замінювати blockout на вже наявні реальні моделі.
6. Довести test weapon rack і first-person presentation.
